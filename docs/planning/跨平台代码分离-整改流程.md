## 二、整改流程总览

**原则**（对齐方案第四节与 AGENTS.md）：

- 按优先级 P0 → P3 分阶段推进，**每阶段一次提交，不混合改动**。
- 每阶段都有明确的验证命令，全部通过后才进入下一阶段。
- 阶段间无强依赖（G1/G4/G6 可并行分支，G2 独立，G5 最后），可按团队节奏插队。
- 不触碰 `apps/routing-tool/`、不改 Wails 版本、不引入三端构建标签（除非出现真实分歧）。

```
阶段 0：现状核查（已完成，见本文件第一节）
阶段 1：P0 · G1 拆分 notify.go（桌面壳，低风险）
阶段 2：P1 · G4 抽取 usePlatform hook（前端，行为不变）
阶段 3：P1 · G6 ci.yml 增加桌面壳编译检查（CI）
阶段 4：P2 · G2 消除路径策略重复（跨模块，中风险）
阶段 5：P2 · G5 release.yml 补全 Linux deb 发布（发布，中风险）
阶段 6：P3 · G3 backend.go 数据目录判断收敛（可选，延后）
```

## 三、分阶段整改详案

### 阶段 1：P0 · G1 拆分 notify.go（独立提交 #1）

**目标**：非 Windows 平台编译期完全不引入 `go-toast`，消除「注释说 noop、实际依赖 catch 吞错」的行为不一致。

**改动文件**（`apps/desktop/`）：

```
notify.go            （改造）共享：startNotifyWatcher、showNativeToast 接口定义
notify_windows.go    （新增）//go:build windows   Windows Toast 实现（依赖 go-toast）
notify_other.go      （新增）//go:build !windows  noop 实现（不引入 go-toast）
window.go            （改造）清理 :322-323 重复注释
```

**拆分规则**：

- `notify.go` 保留 `startNotifyWatcher`（纯轮询逻辑，平台无关）与 `type notifyFunc func(...)` 签名，定义：

  ```go
  // notify.go
  // showNativeToast 发送原生系统通知；非 Windows 平台为 noop。
  func (a *App) showNativeToast(title, body string) error
  ```

- `notify_windows.go`：`registerNotificationApp()` + `showNativeToast()` 用 `go-toast` 实现（把现有 `ShowNotification` 体迁移过来）。

- `notify_other.go`：`registerNotificationApp()` noop + `showNativeToast()` 返回 nil。

- **注意**：`ShowNotification` 是 Wails 绑定方法（`frontend/wailsjs/` 已生成 `ShowNotification`），删除绑定方法会导致前端调用失败。**方案**：保留 `ShowNotification` 作为薄包装：

  ```go
  // notify.go（共享）
  func (a *App) ShowNotification(title, body string) error {
      return a.showNativeToast(title, body)
  }
  ```

  这样 Wails 绑定签名不变，前端无需改动；`startNotifyWatcher` 继续调用 `a.ShowNotification`（或直接 `showNativeToast`，二选一，建议统一走 `ShowNotification` 保持绑定面稳定）。

**验证**（需三端交叉编译，本地 Windows 只能验证 windows + 部分交叉）：

```bash
cd apps/desktop
go build ./...                          # Windows 当前平台
GOOS=linux GOARCH=amd64 go build ./...  # 若桌面壳无 CGO 依赖可交叉编译；失败则靠 CI 验证
go vet ./...
```

> 桌面壳依赖 Wails v2，Linux 交叉编译可能需要 CGO/GTK 头文件，本地可能无法直接交叉验证非 Windows 分支。此时以 `build-desktop.yml` 三端 CI 为准（push 后看矩阵结果）。

**验收**：非 Windows 分支不再出现 `go-toast` 导入；行为与现状一致（Windows 发 Toast，其他平台静默成功）。

### 阶段 2：P1 · G4 抽取 usePlatform hook（独立提交 #2）

**目标**：统一前端平台判断入口，消除 TitleBar/Sidebar 重复代码。

**改动文件**（`apps/web/src/`）：

```
hooks/usePlatform.ts  （新增）统一 hook
components/TitleBar.tsx （改造）替换 platform state
components/Sidebar.tsx  （改造）替换 isMac/macLoading state
```

**实现要点**（对齐方案 3.2.1，补充 Sidebar 语义差异）：

- 方案给出的 hook 返回 `{ platform, isMac, isWindows, isLinux, ready }`。
- **Sidebar 当前用 `macLoading` 区分「平台未知期」**（:146,153,353,364）——`ready` 语义即替代 `macLoading`（`ready === !macLoading`），改造时把 `{isMac && !macLoading && ...}` 换成 `{isMac && ready && ...}`、`{!isMac && !macLoading && ...}` 换成 `{!isMac && ready && ...}`，**行为必须保持完全一致**。
- 平台未知期（`ready === false`）渲染门控保持现状（`TitleBar.tsx:177` 返回 null、Sidebar 顶栏不渲染），避免错版式闪烁。
- `hooks/` 目录现有 7 个 hook，命名风格为 `useXxx.ts`（camelCase），符合。

**验证**：

```bash
cd apps/web
npm run typecheck        # 或 npx tsc --noEmit（对齐 CI）
npm run build:web        # 可选，确保产物正常
```

**验收**：`TitleBar.tsx` / `Sidebar.tsx` 无 `getPlatform` 直接调用；平台判断只出现在 `usePlatform` 与 `api.ts`；渲染行为肉眼无差异（macOS 顶栏/搜索框时序一致）。

### 阶段 3：P1 · G6 ci.yml 增加桌面壳编译检查（独立提交 #3）

**目标**：PR 阶段即可暴露桌面壳构建标签/类型错误，缩短反馈链路。

**改动文件**：`.github/workflows/ci.yml`

**改动内容**（在 `Build Go backend` 步骤后追加）：

```yaml
      # 桌面壳编译检查：拦截 //go:build 标签错误与类型错误（不跑 wails build，成本高）。
      # frontend/dist 有 //go:embed all:frontend/dist，需先建占位目录。
      - name: Desktop compile check
        run: |
          mkdir -p apps/desktop/frontend/dist
          touch apps/desktop/frontend/dist/.gitkeep
          cd apps/desktop && go mod download && go build ./... && go vet ./...
```

> 注意：ci.yml 目前未对 `apps/desktop` 执行 `go mod download`（依赖来自 server/go 的 download），桌面壳有独立 go.mod，必须补 download。X4 建议顺带 `go vet ./...`，成本低、可拦截 gofmt 之外的静态问题。

**验证**：push 后看 CI 绿；本地可先行：

```bash
mkdir -p apps/desktop/frontend/dist && touch apps/desktop/frontend/dist/.gitkeep
cd apps/desktop && go mod download && go build ./... && go vet ./...
```

**验收**：ci.yml 绿时桌面壳 `go build` 通过；故意写错构建标签（如删 `//go:build !windows`）时 CI 变红。

### 阶段 4：P2 · G2 消除路径策略重复（独立提交 #4）

**目标**：`UserDataDir()` 单一实现，消除双份维护。

**改动文件**：

```
server/go/internal/paths/paths.go   （新增）UserDataDir() 唯一实现
server/go/internal/database/database.go  （改造）defaultReaderDBPath 复用
apps/desktop/backend.go             （改造）userDataDirectory 复用
```

**实现要点**：

- 新增叶子包 `server/go/internal/paths/`，实现：

  ```go
  // paths.go
  package paths

  // UserDataDir 返回用户数据目录：
  // Windows: %LOCALAPPDATA%\Flore（回退 %APPDATA%\Flore、%TEMP%\Flore）
  // 其他:    ~/.flore（HOME 不可用时回退当前目录）
  func UserDataDir() string
  ```

- `database.go:40-62` 的 `defaultReaderDBPath()` 改为：

  ```go
  baseDir := paths.UserDataDir()
  ```

- `backend.go:432-446` 的 `userDataDirectory()` 改为 `return paths.UserDataDir()`，删除内联逻辑。

- **X2 关键点**：desktop 的 go.mod 已 `replace github.com/rss/go-server => ../../server/go`，desktop 可直接 `import "github.com/rss/go-server/internal/paths"`，**无循环依赖**（desktop → server 单向，server 不反向 import desktop）。比方案设想的「desktop 不便反向依赖 server」更简单。

- **行为对齐检查**：两处原实现细节必须一致——
  - Windows 回退链：backend 用 `LOCALAPPDATA → APPDATA → os.TempDir()`；database 用 `LOCALAPPDATA → APPDATA → os.TempDir()`。一致 ✅
  - 非 Windows：backend 用 `os.UserHomeDir()` 失败回退 `"."`；database 失败返回 error。**差异**：合并后统一为「回退 `"."`」还是「回退 error」需决策。建议 `UserDataDir()` 返回 `(string, error)`，database 保留错误传播，backend 端回退 `"."` 兼容现有行为。二选一但必须显式记录在 ADR 中。

**验证**：

```bash
cd server/go && go build ./... && go test ./...
cd apps/desktop && go build ./...
```

**验收**：两处调用同一实现；单测覆盖 Windows/非 Windows 路径（可用 `t.Setenv("LOCALAPPDATA", ...)` 模拟）。

### 阶段 5：P2 · G5 release.yml 补全 Linux deb 发布（独立提交 #5）

**目标**：Linux 用户可手动下载 deb 安装包。

**改动文件**：`.github/workflows/release.yml`

**改动内容**：

1. matrix 增加一行：

   ```yaml
           - os: ubuntu-latest
             goos: linux
             goarch: amd64
   ```

2. 新增 Linux 构建步骤（仿照 Windows/macOS 分支）：

   ```yaml
       # ---- Linux：deb 安装包 ----
       - name: Build & package (Linux)
         if: matrix.goos == 'linux'
         shell: bash
         run: |
           VERSION="${{ github.event_name == 'workflow_dispatch' && github.event.inputs.version || github.ref_name }}"
           VERSION="${VERSION#v}"
           cd apps/desktop
           node sync-version.mjs "$VERSION"
           wails build -ldflags "-X github.com/rss/go-server/internal/handlers.appVersion=$VERSION"
           # 需要 GTK/WebKit 依赖与 dpkg-deb（X3）
           sudo apt-get update
           sudo apt-get install -y dpkg-dev
           go run ./cmd/package-tool -edition deb -version "$VERSION" -os linux -arch amd64 -feBin build/bin/Flore
   ```

3. 上传 artifact 的 path 增加 `*.deb`。

4. **发布步骤（release job）**：
   - GitHub Release：assets 数组增加 `flore_<version>-1_amd64.deb`（`package-tool` 输出命名 `flore_<ver>-1_<arch>.deb`）。
   - R2：**不进自动更新清单**（`update.json` 的 `-platforms windows,darwin` 保持不变），不上传 deb 到 R2——因为 `updater/apply_other.go` 非 Windows 直接报错，Linux 自动更新未实现（方案第六节第 6 条）。

**验证**：本地无法完整验证 CI，但可验证 package-tool deb 分支逻辑（需 Linux 环境或 WSL）。推送 tag 后人工下载 deb 实测安装：

```bash
sudo dpkg -i flore_0.1.0-20260805-1_amd64.deb   # 依赖 dpkg-deb 生成的包结构
```

**验收**：release.yml 跑出 6 个包（win zip+exe、mac zip+dmg、linux deb）；GitHub Release 可下载 Linux deb；`update.json` 仍只含 windows/darwin。

**目标**：`backend.go` 内联 `runtime.GOOS` 判断是否拆构建标签。

## 四、风险与回滚

| 风险 | 影响阶段 | 缓解 |
|------|---------|------|
| G1 拆分后非 Windows 分支编译失败 | 1 | 靠 `build-desktop.yml` 三端矩阵验证；`showNativeToast` 接口两平台必须同签名 |
| G4 改造改变 Sidebar 搜索框时序 | 2 | `ready` 与 `macLoading` 语义一一对应；改造前后肉眼对比 macOS/Windows 渲染 |
| G2 统一路径后行为漂移（Windows 回退链） | 4 | 单测覆盖；改动前先跑一次完整导出/备份冒烟 |
| G5 引入 Linux 构建拉长 release 时长 | 5 | Linux job 与 win/mac 并行（matrix），不串行；fail-fast: false 已配 |
| 每阶段提交独立，回滚互不影响 | 全部 | 严格单提交；异常时 `git revert <commit>` 仅回滚该阶段 |

## 五、提交顺序建议

按仓库节奏，推荐两批：

- **第一批（低风险，可并行）**：提交 #1（G1）、#2（G4）、#3（G6）——三者文件域互不重叠（desktop Go / web 前端 / CI）。
- **第二批（中风险，顺序执行）**：提交 #4（G2，需先确认 `UserDataDir()` 行为决策）→ 提交 #5（G5，依赖 #4 稳定后发版验证）。

> 每批完成后跑一次完整三端构建（本地 wails build 或 push 触发 build-desktop.yml），确认无回归再进入下一批。
