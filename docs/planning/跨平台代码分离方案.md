# 跨平台代码分离方案

> 适用范围：Flore（Go + Wails）桌面应用，目标平台 Windows / Linux / macOS。
> 编写时间：2026-08-10。
> 参考依据：`docs/planning/DeepSeek - 多端应用不分端分支.md`（DeepSeek 给出的 Wails 项目不分端分支建议）。

---

## 一、背景与目标

Flore 已完成 Windows / Linux / macOS 三端构建，各端可正常运行。本方案回答一个问题：**如何在单仓库单分支的前提下，规范地分离不同平台的代码与资源**。

核心结论与 DeepSeek 文档一致：

- **绝不为每个平台开 Git 分支**。Git 分支用于管理开发阶段与发布版本，不用于隔离运行环境。
- 平台隔离交给 Go 构建标签（`//go:build`）+ 运行时判断（`runtime.GOOS`）+ 前端条件渲染 + `build/` 子目录资源隔离 + CI matrix 构建来完成。
- 项目只需维护 `main`（可发布）与 `dev`（开发）两个长期分支。

Flore 的现状已经基本符合这一思路，本方案的重点是**把已有的零散实践收敛为统一约定，并补齐少量缺口**，而非推倒重来。

## 三、分离策略

### 3.1 Go 后端：构建标签 + 运行时判断分层

**原则**：编译期可确定的差异用构建标签，运行期才能确定的差异用 `runtime.GOOS`。

#### 3.1.1 构建标签命名约定

项目当前用 `windows` / `!windows` 二分法。本方案规范化为两种模式，按场景选择：

**模式 A：仅 Windows 有特殊实现（保持现状）**

适用于「只有 Windows 需要特殊处理，其他平台共享同一份 noop/通用实现」的场景。继续用 `_windows.go` + `_other.go`。

```
foo_windows.go   //go:build windows
foo_other.go     //go:build !windows
```

当前 `dialog_*.go`、`job_*.go`、`updater/apply_*.go` 属于此类，**保持不变**。

**模式 B：三端均有差异（按需引入）**

当 darwin 与 linux 的实现也确实不同时，才拆为三份。不要为「未来可能不同」提前拆分。

```
foo_windows.go   //go:build windows
foo_darwin.go    //go:build darwin
foo_linux.go     //go:build linux
```

**判断标准**：若 darwin 与 linux 实现完全一致，用模式 A；只有真正分歧时才用模式 B。当前项目无模式 B 场景。

#### 3.1.2 运行时判断的使用边界

`runtime.GOOS` 适用于「差异是小分支，主体逻辑共享」的场景。当前 `backend.go` 的数据目录判断、`main.go` 的窗口装饰判断属于此类，**保持内联即可**，不必强行拆成构建标签文件。

但需遵守：

- 同一差异点不要在多个文件重复判断（见 G2 改造）。
- 判断结果若被多处使用，封装为单一函数（如 `GetPlatform()`）。

#### 3.1.3 改造项：修复 notify.go 平台缺口（G1）

将 `notify.go` 拆为构建标签文件，让 Windows 专用依赖只在 Windows 编译期引入：

```
notify.go            共享：接口定义、watcher 逻辑、noop 兜底
notify_windows.go    //go:build windows    Windows Toast 实现（依赖 go-toast）
notify_other.go      //go:build !windows   调用 noop，不引入 go-toast
```

`notify.go` 定义 `showNativeToast(title, body string) error`，`notify_windows.go` 与 `notify_other.go` 各自实现。这样非 Windows 平台编译期完全不引入 `go-toast`，消除「静默失败依赖 catch 吞错」的隐患。

#### 3.1.4 改造项：消除路径策略重复（G2）

`apps/desktop/backend.go` 与 `server/go/internal/database/database.go` 各自实现了「Windows 用 LOCALAPPDATA，其他用 ~/.flore」。建议：

- 在 `server/go/internal/database/` 或新增的共享包中提供 `UserDataDir() string` 单一实现。
- `apps/desktop/backend.go` 的 `userDataDirectory()` 改为调用该实现（或两者都委托给同一个函数）。
- 避免跨模块循环依赖：若 desktop 不便反向依赖 server，可把路径工具下沉到一个无业务依赖的小包（如 `server/go/internal/paths/`），desktop 通过 replace 或复制极薄包装引用。

> 注：此改造涉及跨模块依赖调整，单独一次提交完成，不与平台分离改造混在一起。

### 3.2 前端：统一平台判断入口

#### 3.2.1 改造项：抽取 `usePlatform` hook（G4）

当前 `TitleBar.tsx` 与 `Sidebar.tsx` 各自维护 `platform` state + `useEffect` 调 `getPlatform()`。抽取统一 hook：

新增 `apps/web/src/hooks/usePlatform.ts`：

```ts
import { useEffect, useState } from 'react';
import { getPlatform } from '../utils/api';

// 平台标识：'windows' | 'darwin' | 'linux' | ''（Web 或未就绪）
export type Platform = 'windows' | 'darwin' | 'linux' | '';

export function usePlatform() {
  const [platform, setPlatform] = useState<Platform>('');
  useEffect(() => {
    let cancelled = false;
    getPlatform().then((p) => {
      if (!cancelled) setPlatform((p as Platform) || '');
    });
    return () => { cancelled = true; };
  }, []);
  return {
    platform,
    isMac: platform === 'darwin',
    isWindows: platform === 'windows',
    isLinux: platform === 'linux',
    ready: platform !== '',
  };
}
```

`TitleBar.tsx`、`Sidebar.tsx` 改为调用 `usePlatform()`，删除各自的 `platform` state 与 `useEffect`。后续新增平台判断点统一用此 hook。

#### 3.2.2 条件渲染约定

- 平台未确定（`platform === ''`）时，渲染 `null` 或骨架屏，避免错版式闪烁。`TitleBar.tsx:177` 已遵循此约定。
- 平台差异尽量收敛在布局层（TitleBar、Sidebar），业务组件不直接判断平台。
- 桌面/Web 差异用 `isDesktop()`，平台差异用 `usePlatform()`，二者职责分开，不混用。

### 3.3 构建资源隔离

#### 3.3.1 `build/` 子目录约定（保持现状）

```
apps/desktop/build/
├── appicon.png              跨平台共用图标
├── favicon.ico
├── darwin/
│   ├── Info.plist           macOS 生产配置
│   └── Info.dev.plist       macOS 开发配置
└── windows/
    ├── icon.ico             Windows 图标
    ├── info.json            Windows 版本信息
    ├── wails.exe.manifest   Windows 清单
    └── installer/           NSIS 安装器脚本
        ├── project.nsi
        └── wails_tools.nsh
```

Wails 构建时会自动到对应子目录找资源，无需在代码里判断平台。**新增平台资源一律放入对应子目录，不放 `build/` 根目录**。

#### 3.3.2 Linux 资源补全

当前 `build/` 下无 `linux/` 子目录。Linux 桌面图标、`.desktop` 文件、AppStream metadata 可按需新增：

```
apps/desktop/build/linux/
├── icon.png                 Linux 图标（已由 appIcon embed 提供，可选）
├── flore.desktop            桌面入口文件
└── flore.appdata.xml        AppStream 元数据（供软件中心展示）
```

仅在需要发布 deb/rpm 或接入软件中心时新增，避免提前造资源。

### 3.4 CI/CD 多端构建

#### 3.4.1 现状矩阵

| Workflow | 触发 | 矩阵 | 产物 |
|----------|------|------|------|
| `ci.yml` | push/PR 到 main | ubuntu 单端 | gofmt/vet/test/tsc/build，**不构建桌面壳** |
| `build-desktop.yml` | push/PR 到 main、tag | windows/darwin/linux 三端 | 桌面二进制 artifact |
| `release.yml` | tag / 手动 | windows/amd64 + darwin/arm64 | 便携包 + 安装包 + R2 + GitHub Release |

#### 3.4.2 改造项：补全 Linux 发布（G5）

`release.yml` 当前只覆盖 Windows 与 macOS。若需要 Linux 安装包（deb/rpm），扩展 matrix：

```yaml
matrix:
  include:
    - os: windows-latest
      goos: windows
      goarch: amd64
    - os: macos-latest
      goos: darwin
      goarch: arm64
    - os: ubuntu-latest
      goos: linux
      goarch: amd64
```

Linux 步骤用 `package-tool -edition deb` 生成 deb 包（`cmd/package-tool/main.go:137` 已支持）。是否纳入自动更新清单（`update.json`）取决于是否要给 Linux 提供自动更新——当前 `updater/apply_other.go` 对非 Windows 直接报错，Linux 自动更新需先实现 `apply_linux.go`，**建议先只发布手动下载的 deb，不进自动更新清单**。

#### 3.4.3 改造项：CI 增加桌面壳编译检查（G6）

`ci.yml` 在 ubuntu 上不构建桌面壳，桌面壳的编译错误（如 `//go:build` 标签写错、`frontend/dist` embed 缺失）只能由 `build-desktop.yml` 暴露。建议在 `ci.yml` 增加一步轻量编译检查：

```yaml
- name: Desktop compile check (linux)
  run: |
    mkdir -p apps/desktop/frontend/dist
    touch apps/desktop/frontend/dist/.gitkeep
    cd apps/desktop && go build ./...
```

只做 `go build`，不做 `wails build`（后者需要 GTK/WebKit 依赖，CI 成本高）。这一步能拦截构建标签错误与类型错误，与 `build-desktop.yml` 的完整构建互补。

#### 3.4.4 版本号注入链路（保持现状）

```
package.json (version)
    │
    ├── sync-version.mjs → version.go + wails.json productVersion
    │
    └── wails build -ldflags -X ...handlers.appVersion=$VERSION
            └── /api/version 返回，前端 SettingsAboutTab 显示
```

此链路已跨平台统一，**保持不变**。`release.yml` 与 `build-desktop.yml` 都通过 `sync-version.mjs` 注入，无平台分支。

## 六、风险与注意事项

1. **构建标签与 `runtime.GOOS` 不要重复**。同一差异点要么用构建标签（编译期分流），要么用 `runtime.GOOS`（运行期分流），不要两者混用，否则维护时容易看错分支。

2. **`!windows` 兜底要显式 noop**。`job_other.go`、`dialog_other.go` 的 noop 实现不能省略——调用方依赖这些函数签名存在，省略会导致非 Windows 编译失败。参考 `job_other.go:18,21,24` 的写法。

3. **构建标签文件不能有运行时副作用差异**。同一函数签名在不同平台文件中的行为差异要可预测。`notify.go` 当前的问题正是「注释说 noop，实际依赖 catch 吞错」，行为不可预测，必须修复。

4. **前端平台判断是异步的**。`getPlatform()` 返回 Promise，组件 mount 时 `platform` 为空串。所有依赖平台的渲染都要先判 `ready` 或 `platform === ''`，否则会闪烁错版式。`TitleBar.tsx:177`、`Sidebar.tsx` 都已遵循。

5. **跨模块路径策略统一要避免循环依赖**。G2 改造时，路径工具包必须是无业务依赖的叶子包，不能反向引用 handler/service。

6. **Linux 自动更新暂不支持**。`updater/apply_other.go` 对非 Windows 直接报错。若要支持 Linux 自动更新，需新增 `apply_linux.go` 实现（替换 AppImage/deb 安装脚本），这是独立功能，不在本方案范围。

7. **macOS 未签名公证**。`release.yml:21` 已说明 macOS 包未做 Apple 签名，Gatekeeper 会拦截。这是发布策略问题，与代码分离无关，但改造 Linux 发布时要注意不要把未签名包写入自动更新清单。

## 七、与 DeepSeek 文档的对照

| DeepSeek 建议 | Flore 现状 | 本方案 |
|--------------|-----------|--------|
| 单仓单分支，用文件夹区分平台 | 已是单仓单分支 | 维持，写为约定 |
| Go 用 `_platform.go` 后缀 + 构建标签 | 已用 `_windows.go`/`_other.go` | 规范化命名约定（第 5.1 节） |
| 前端用 `GetPlatform()` + 条件渲染 | 已有 `GetPlatform()` 绑定 | 抽取 `usePlatform` hook 统一入口 |
| 资源放 `build/` 子文件夹 | 已按 `darwin/`、`windows/` 分 | 补 `linux/` 子目录约定 |
| 一条命令打三端 | `build-desktop.mjs` 按当前平台构建 | CI matrix 已实现三端，本地按平台构建 |
| 只维护 `main` + `dev` | 现状如此 | 维持 |

Flore 的实践已覆盖 DeepSeek 文档的全部建议，本方案的工作量集中在**补齐 notify.go 缺口、抽取前端 hook、补全 Linux 发布、消除路径策略重复** 四个点，不涉及架构调整。
