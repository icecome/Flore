## 3. 同类项目实现对比

| 维度 | **本项目 Flore** | **Folo** | **Fluent Reader** |
|------|----------------|----------|-------------------|
| 全文提取 | Go 后端 `go-shiori/go-readability`，返回 `Content` HTML | Node 端 `@mozilla/readability`（linkedom 解析），**提取前**归一化 | `fetch(link)` 抓整页 HTML，用 webview 渲染（非智能提取） |

| 懒加载 `data-src` | ❌ 只认 `src`；DOMPurify `ALLOW_DATA_ATTR:false` 还会**剥离** `data-*` → 图消失 | ✅ 依赖 Readability 内部把 `data-src→src`，且已转绝对 | N/A（webview 内 JS 执行懒加载） |
| `srcset` / `<picture>` | ❌ `rewriteImageUrls` 不处理 | 部分（渲染层统一图片组件处理） | N/A |
| 图片代理 | ✅ `/image-proxy`（带 referer 防盗链绕过 + 重试 + 类型白名单） | ✅ 独立服务 `img.folo.is`，**按 CDN 定制的 referer 规则表**（微博/小红书/pixiv 等）+ 尺寸缩放 | ❌ 无（webview 内核直接加载原图） |
| 渲染容器 | 网页模式用 `<iframe srcdoc>`/`src`；全文模式用 `dangerouslySetInnerHTML` | 自研组件树，图片统一走 `LazyImage` 代理组件 | Electron `<webview>`（真实 Chromium 内核，JS 执行、登录态、sandbox 分区） |
| 网页模式策略 | 桌面端 `mode=minimal`（**资源直连原站**）；Web 端默认（内联 CSS + 图片代理） | 主要 readability 全文 + 图片代理；查看原文多为新标签/iframe | `<webview src=原文URL>` 直接加载，partition=sandbox |
| 反防盗链能力 | 仅 image-proxy 带 referer；minimal 直连时无 referer | 代理服务 + CDN 规则表 + 可伪造 referer | webview 真实浏览器请求，自带正确 referer/cookie |

**核心结论**：
- Folo 的确定性最高来源于「**提取前就做 URL 归一化** + **渲染层统一图片代理组件**」两层保障。
- Fluent Reader 的网页模式体验最好，因为它用「真实浏览器内核（webview）」而非 iframe 代理——代价是依赖 Electron，且仍需面对站点主动反嵌入 JS。
- 本项目的全文模式把「归一化」这一关键步骤遗漏了，且前端重写函数能力弱于后端已有的 `rewriteImageURLs`，导致两类图片问题。

## 4. 问题根因定位

### 4.1 问题一：全文模式部分文章抓不到图片

调用链：`后端 FetchReadability` → 返回 `article.Content` → 前端 `fetchReadability` → `rewriteImageUrls(content, item.link)` → `DOMPurify.sanitize(...)` → 渲染。

`rewriteImageUrls`（`Reader.tsx:62-83`）只匹配 `<img src>`，存在三个确定性缺陷：

- **M-R1 相对路径未解析**：`go-readability` 返回的 `Content` 中图片可能是相对 URL（如 `/uploads/a.jpg`）。`rewriteImageUrls` 不解析相对路径，直接拼成 `/image-proxy?url=/uploads/a.jpg`。后端 `FetchImage` 经 `ValidateURLOnly` 要求绝对 `http(s)` URL → **拒绝**。凡图片用相对路径的文章，全部抓取不到图。

- **M-R2 懒加载 `data-src` 被双重丢失**：大量站点用 `<img data-src="...">` 或 `data-original`/`data-lazy-src` 懒加载。`rewriteImageUrls` 只找 `src`，找不到 `data-src`；随后 `DOMPurify.sanitize(..., PURIFY_CONFIG)` 中 `ALLOW_DATA_ATTR:false` 把 `data-*` 属性**整条剥离**。结果：图片既无 `src`、又丢了 `data-src` → 彻底不显示。这正是「未发现规律、部分文章丢图」的主因（取决于该站是否用懒加载）。

- **M-R3 `srcset` / `<picture>` 未处理**：响应式图片用 `<picture><source srcset>` 或 `<img srcset>` 提供多分辨率。`rewriteImageUrls` 不处理 `srcset`/`<source>`，这些 URL 保持原始（相对或绝对无 referer），导致响应式图首选/备用源失效。

> 对照：本项目**后端已有**更完整的 `rewriteImageURLs`（`reader.go:1557`，处理 src/srcset/source/style url()+相对路径解析），但**全文模式未复用**，前端用了能力更弱的另一套 `rewriteImageUrls`（见 m-01）。

### 4.2 问题二：网页模式三种异常

调用链（桌面端）：`Reader.tsx` 检测 `isDesktop()` → `fetch('/proxy/{id}?mode=minimal')` → 后端 `ProxyOriginal` 仅「剥离 CSP meta + 注入 `<base>`」→ `<iframe srcdoc>` 渲染，资源（CSS/JS/图片）**由浏览器直接从原文站点加载**。

三种异常根因：

- **正常打开**：站点允许被 iframe 嵌入、资源无防盗链、无混合内容 → 正常。
- **能打开但缺元素/图片（M-A1 + m-03）**：`mode=minimal` 让资源直连原站，暴露两个原站约束：
  1. **防盗链**：原文图片 CDN 校验 `Referer`，而 srcdoc iframe 的请求 `Referer` 为空 / opaque origin / 应用源，与原站域名不符 → 图片 403。
  2. **混合内容**：若应用以 https 提供，srcdoc 内加载 `http://` 图片/CSS 会被浏览器拦截。
- **只能打开完全样式但错误/空白页（M-R4）**：站点用 JS 主动检测被嵌入（`window.top !== window.self` 或 `window.parent !== window`），随即重定向到首页、插入遮罩、或渲染登录页。minimal 模式 `sandbox="allow-scripts"` 允许 JS 执行，故此类防御完全生效。

> 关于 `X-Frame-Options`：经核实 `ProxyOriginal` 仅 `c.Header("Content-Type", ...)`，**不会**转发原站响应头，且 meta CSP 已被 `stripCSPMetaTags` 剥离，因此「HTTP 头 X-Frame-Options 透传拦截」在本实现中**不是**主因；主因是上述防盗链、混合内容与站点 JS 反嵌入。

## 5. MAJOR 问题详情

### M-R1: 全文模式相对路径图片被 image-proxy 拒绝
- **文件**：`apps/web/src/components/Reader.tsx:62-83`（`rewriteImageUrls`）
- **类别**：可靠性
- **问题**：函数未对 `src` 做相对路径→绝对路径解析，相对 URL 直接传给 `/image-proxy?url=<相对路径>`，后端 `ValidateURLOnly` 拒绝。
- **影响**：所有以相对路径引用图片的文章，全文模式图片全部缺失。
- **建议修复**：见第 6 节方案 A（后端归一化为首选，或前端用 `new URL(src, articleUrl)` 解析）。

### M-R2: 懒加载 data-src 图片被 DOMPurify 剥离
- **文件**：`Reader.tsx:35-42`（PURIFY_CONFIG `ALLOW_DATA_ATTR:false`）、`Reader.tsx:62-83`（`rewriteImageUrls` 只认 src）
- **类别**：可靠性
- **问题**：`data-src` 等懒加载属性在 sanitize 阶段被剥离，且重写阶段未将其转为 `src`。
- **影响**：使用懒加载的站点全文模式图片消失。
- **建议修复**：在 sanitize **之前**将 `data-src`/`data-original`/`data-lazy-src` 归一化为 `src`（后端归一化更稳，见方案 A）。

### M-R3: srcset / `<picture>` 未重写
- **文件**：`Reader.tsx:62-83`
- **类别**：可靠性
- **问题**：`rewriteImageUrls` 未覆盖 `srcset` 与 `<source srcset>`。
- **影响**：响应式图片源失效，部分文章主图/配图缺失。
- **建议修复**：复用后端 `rewriteImageURLs` 的 srcset/source 处理逻辑（前端实现 `rewriteSrcset` 已存在于 `Reader.tsx:89` 但未被 `rewriteImageUrls` 调用）。

### M-A1: 网页模式桌面端 minimal 直连原站资源不可控
- **文件**：`Reader.tsx:541-557`（桌面端走 `?mode=minimal`）、`reader.go:1170-1179`（`mode=minimal` 不内联 CSS / 不重写图片）
- **类别**：架构
- **问题**：minimal 模式把 CSS/JS/图片的加载完全交给原文站点，使防盗链、混合内容、站点 JS 反嵌入全部暴露，且与 Web 端默认代理行为不一致。
- **影响**：网页模式在大量站点上缺图/缺样式/被拦截。
- **建议修复**：桌面端改走**完整代理模式**（同 Web 端：内联 CSS + 图片重写），见方案 B。

### M-R4: 网页模式对站点 JS 反嵌入无检测与 fallback
- **文件**：`Reader.tsx:535-563`、`reader.go:1119-1197`
- **类别**：可靠性
- **问题**：当站点用 JS 检测 iframe 并重定向/覆盖时，用户只能看到破损或错误页，无任何提示与降级。
- **影响**：部分站点网页模式不可用且无出路。
- **建议修复**：检测异常（重定向 URL 变化、body 内容含已知 anti-frame 特征、或渲染高度异常）时，提示「该站点禁止内嵌，建议在新窗口打开」并提供 `openExternal` 入口（见方案 B）。

## 8. 最优解方案（可落地）

### 8.1 全文模式：后端归一化 + 前端增强（对齐 Folo）

**原则**：全文内容由后端产出，应返回「可直接用的干净 HTML」——相对路径转绝对、懒加载属性归一化。前端只负责把 `src` 重写为 image-proxy。

**步骤 1（后端，首选，P0）**：在 `readability.go` 的 `FetchReadability` 返回前，对 `article.Content` 做归一化。建议新增 `normalizeContent(content, articleURL string) string`，用 `goquery` 遍历：

```go
// 相对路径 -> 绝对路径（基于 articleURL）
doc.Find("img, audio, video, source").Each(func(_, s *goquery.Selection) {
    for _, attr := range []string{"src", "srcset", "data-src", "data-srcset", "data-original", "data-lazy-src"} {
        if v, ok := s.Attr(attr); ok && v != "" {
            // srcset 需逐个 URL 解析
            abs := toAbsolute(v, articleURL) // 相对 -> 绝对
            if attr == "src" || attr == "data-src" || attr == "data-original" || attr == "data-lazy-src" {
                if s.AttrOr("src", "") == "" {
                    s.SetAttr("src", abs) // 懒加载属性归一到 src（DOMPurify 会剥 data-*）
                }
            } else {
                s.SetAttr(attr, abs)
            }
        }
    }
})
```

> 说明：`go-shiori/go-readability` 本身已部分处理懒加载，但显式归一化可消除版本差异与「data-original」等非标准属性，覆盖更全。归一化后 DOMPurify 即便剥离 `data-*`，`src` 已存在，图片不丢。

**步骤 2（前端，P1）**：把 `rewriteImageUrls` 升级为与 `rewriteSrcset` 协同，并解析相对路径（兜底）：

```ts
function rewriteImageUrls(html: string, articleUrl?: string): string {
  // 1) 先归一化懒加载属性（在 sanitize 之前）
  html = normalizeLazyImages(html, articleUrl) // data-src/data-original -> src，并用 articleUrl 解析相对路径
  // 2) 重写 src + srcset（复用已有 rewriteSrcset）
  html = html.replace(/<img\s([^>]*?)\/?>/gi, (match) => {
    // 解析 src 相对路径 + 重写 srcset
  })
  return html
}
```

**步骤 3（去重，P2/n-02）**：将 `rewriteImageUrls`、`rewriteSrcset`、`rewriteIframeContent` 合并为一个通用 `rewriteAllMedia(html, baseURL)` 工具，全文模式与网页模式共用。

**预期收益**：解决 M-R1/M-R2/M-R3/m-01/m-02，覆盖绝大多数「全文抓不到图」的文章。

### 8.2 网页模式：桌面端统一完整代理 + 反嵌入 fallback

**原则**：桌面端放弃 minimal 直连，复用 Web 端已验证的完整代理（内联 CSS + 图片走 `/image-proxy`），从根上解决防盗链与混合内容。

**步骤 1（P0）**：`Reader.tsx` 桌面端也请求默认模式（去掉 `?mode=minimal`）：

```ts
if (isDesktop() || !item.link) {
  const res = await fetch(`${getApi()}/proxy/${item.id}`); // 默认模式：内联 CSS + 图片代理
  const html = await res.text();
  setIframeContent(html);
}
```

后端 `mode != "minimal"` 分支已做 `inlineExternalCSS` + `rewriteImageURLs`，图片经 `/image-proxy`（带 referer）抓取，http 资源由 https 代理回源 → **消除混合内容**与**防盗链**。

**步骤 2（P1，M-R4 fallback）**：`onLoad` 后检测反嵌入异常：

```ts
const onIframeLoad = () => {
  setLoadingIframe(false);
  // 检测：srcdoc 内发生顶层重定向 / body 高度异常 / 含 anti-frame 特征
  // 若异常 -> 显示提示条：「该站点禁止内嵌显示，建议在新窗口打开」+ openExternal 按钮
};
```

> 站点 JS 主动反嵌入（重定向/覆盖）属根本性限制，任何 reader 都无法 100% 绕过；正确做法是**检测 + 优雅降级到浏览器打开**，而非强行内嵌。

**步骤 3（P1，m-03）**：若仍保留 minimal 作为可选项，则对直连资源补 `Referer`（需后端注入 `<base>` 外再注入 meta referrer policy `no-referrer-when-downgrade`），但推荐直接用步骤 1 的完整代理，避免双路径维护。

**预期收益**：解决 M-A1/m-03/m-04，网页模式「缺图/缺样式」大幅减少；对无法内嵌的站点给出明确出路（M-R4）。

## 12. 网页模式 WebView2 回归链路与最终根因（2026-07-31 第二轮）

> 第一轮落地后，网页模式在桌面端（Wails/WebView2）反复出现「已阻止此内容」「纯 HTML 文本」「无样式」三类异常。经逐轮排查，定位真正根因不在 CSP，而在**服务端内联 CSS 策略**。

### 12.1 回归链路（按时间）

| 轮次 | 改动 | 现象 | 误判根因 |
|------|------|------|---------|
| A | 桌面端 `srcdoc` + `mode=minimal` 改 `src` + iframe `csp` 属性 | 纯 HTML 文本 / 固定网页 | srcdoc 缓存 + 长 HTML 解析异常 |
| B | 桌面端改 `src` 加载 `/proxy/{id}`（仍带 `csp` 属性） | 能切文章但**无样式** | 以为缺 `csp` 属性 |
| C | 加回 `csp` 属性 | **已阻止此内容**（整页被拦） | WebView2 对 iframe `csp` 属性处理异常 |
| D | 移除 `csp` 属性 + 改由响应头下发 CSP | **仍无样式** | 误以为 CSP 头未生效 |
| E（最终） | 移除响应头 CSP + **停止服务端内联 CSS**（浏览器直连原站 CSS/JS，仅代理图片） | 样式恢复 + 图片代理生效 | 见 12.2 |

### 12.2 真正根因

`ProxyOriginal` 非 minimal 路径调用 `inlineExternalCSS`：**服务端 `FetchCSS` 抓取原文 CSS** 内联成 `<style>`。

- 原站对 CSS 做 Referer 防盗链 / 服务端抓取超时失败时，`processSingleLink` 降级到 `/css-proxy`；
- 一旦内联链路整体失败，整页 CSS 丢失 → 表现为「无样式」；
- 经验证据：`mode=minimal`（浏览器**直连**原站 CSS）在用户环境**样式正常**，全量代理（内联 CSS）**无样式** → 内联策略是元凶。

关键认知：

- **CSS/JS 资源加载不能使用 iframe `csp` 属性**（WebView2 会拦截整个文档 → 「已阻止此内容」）；
- 仅靠**响应头 CSP** 无法挽救内联失败导致的无样式；
- 真实浏览器内核（WebView2 / Electron webview）**直连原站**加载 CSS/JS 最可靠——这正是 Folo、Fluent Reader 的通用做法。

### 12.3 最终修复（`server/go/internal/handlers/reader.go` `ProxyOriginal`）

1. 删除 `if mode != "minimal"` 分支，**不再调用 `inlineExternalCSS`**；
2. HTML 处理改为：**仅代理图片**（`rewriteImageURLs` → `/image-proxy`，设正确 Referer 绕过防盗链），**CSS/JS 保持原站直连**；
3. 移除 4 处 `Content-Security-Policy` 响应头与 `proxyCSP` 常量，隔离完全交由 iframe `sandbox="allow-scripts allow-popups allow-forms"`（**不含 `allow-same-origin`**，脚本运行在 opaque origin，无法访问父窗口，同时天然阻断站点 JS 的 `window.top` 反嵌入重定向）。

前端 `Reader.tsx` 无需改动：桌面端仍 `src` 加载 `/proxy/{id}`（无 mode 参数 → 走默认直连 CSS + 代理图片路径），iframe 无 `csp` 属性。

### 12.4 验证

- `go build ./...` → 0 错；`go vet ./internal/handlers/...` → 0 错
- 行为对齐已验证可用的 `mode=minimal`（样式可靠）+ 新增图片代理（修复原始需求）

### 12.5 取舍

- **保留 `inlineExternalCSS` 等函数为死代码**：属重构范畴，遵循「修复 Bug 时不重构」原则暂缓清理；`/css-proxy` 路由保留为可达孤儿端点（无害）。
- **少数强检测站点**仍可能因自身 JS 逻辑导致空白，但 sandbox 无 `allow-same-origin` 已阻断其对父窗口的导航/重定向，风险可控。

## 13. 第三轮回归：`<style>` 标签被意外剥离 + 参考项目再次深探（2026-07-31）

### 13.1 现象

用户反馈：网页模式能切换不同文章，但**样式部分渲染、部分完全不渲染**，页面底部/中部出现**裸 CSS 代码文本**（如 `.network-status { ... }`、`.backToTopBtn { ... }`）。

### 13.2 参考项目再次深探结论

| 项目 | 容器 | HTML 代理 | CSS/JS | 图片 | 嵌入限制处理 |
|------|------|-----------|--------|------|--------------|
| **Folo 桌面** | Electron `<webview>` | 无 | 直连原站 | 条件走 `img.folo.is`；桌面 webview 用 `onBeforeSendHeaders` 伪造 Referer | **完全不处理**——webview 是顶层浏览上下文，`X-Frame-Options`/`frame-ancestors` 不生效 |
| **Folo Web** | `<iframe>` | 无 | 直连原站 | 命中规则则走 `img.folo.is` | 无降级，遇到 `DENY` 站点静默失败 |
| **Fluent Reader** | Electron `<webview>` | 无 | 直连原站 | 完全直连，无代理 | **完全不处理**——同 Folo |

核心启示：
- **webview 直接加载原文 URL 是最干净方案**，无需代理 HTML、无需剥离 CSP、无需内联 CSS。
- Flore 用 Wails + WebView2，**没有 `<webview>` 标签**，只能继续 iframe + 代理 HTML 的折中；但应让浏览器尽量直连原站 CSS/JS，仅对图片做代理。

### 13.3 真正根因：Flore 代理 bug

`server/go/internal/handlers/reader.go` `rewriteImageURLs` 第三步重写 `<style>` 内 `url()` 时：

```go
styleRe := regexp.MustCompile(`(?is)<style[^>]*>([\s\S]*?)</style>`)
result = styleRe.ReplaceAllStringFunc(result, func(match string) string {
    content := styleRe.FindStringSubmatch(match)
    css := content[1]
    rewritten := /* 重写 css 内部的 url() */
    return strings.Replace(match, content[0], rewritten, 1)  // ← BUG
})
```

`content[0]` 是完整 `<style>...</style>`，而 `rewritten` 只是内部 CSS 文本。`strings.Replace` 把**整个样式标签外壳替换成了内部文本**，导致：
- `<style>` 与 `</style>` 被删除；
- CSS 规则直接暴露在 `<body>` 中，被浏览器渲染为可见文本；
- 对应样式全部失效。

这与截图中「CSS 代码外露、样式部分丢失」完全吻合。

### 13.4 修复

#### 13.4.1 保留 `<style>` 外壳

改为只替换内部 CSS 文本：

```go
return strings.Replace(match, content[1], rewritten, 1)
```

#### 13.4.2 扩展懒加载图片代理

`<img>` 重写从只处理 `src`/`srcset`，扩展为同时处理 `data-src`、`data-original`、`data-srcset`，覆盖常见懒加载实现。

### 13.5 验证

- `go build ./...` → 0 错
- `go vet ./internal/handlers/...` → 0 错

### 13.6 取舍与长期方向

- **继续保留 iframe + 代理 HTML**：Wails 当前没有等价于 Electron `<webview>` 的嵌入式原生 webview 容器；彻底对齐 Folo/Fluent Reader 需要引入平台相关 WebView2 API 或迁移框架，超出本次 Bug 修复范围。
- **直连 CSS/JS + 代理图片**是现有架构下的最优折中：修复 style 标签剥离后，`<style>` 内图片/字体 `url()` 也会正确走 `/image-proxy`，样式与图片同时受益。
- **残留风险**：少数站点的 CSS 本身做 Referer 防盗链，或依赖 Cookie/LocalStorage 的 JS 在 sandbox 无 `allow-same-origin` 下失败。这类站点在 iframe 方案里无法完美还原，长期建议通过原生 webview 窗口解决。
