## 跨平台构建改造（修复 macOS 上 npm run build 失败）
- 问题：`npm run build` 在 macOS 报错 "前端二进制未找到: build/bin/Flore.exe（请先 wails build）"。
- 根因：根 package.json 的 `build` 链路写死 Windows —— `build:go` 后端输出硬编码 `florebackend.exe`；`build:desktop` 给 `package-tool` 写死 `-os windows -arch amd64`；且 `%npm_package_version%` 语法仅 Windows cmd 展开。导致 macOS 上 wails build 产出 Flore.app 后，package-tool 去找 Flore.exe 报错。
- 方案：新增 `scripts/build-desktop.mjs` Node 跨平台编排器（用户确认选此方案，优于继续在 npm 脚本里用 node -e 拼命令）。自动检测 `process.platform/arch` → 映射为 windows/darwin/linux 与 amd64/arm64；串起 go build 后端（正确扩展名）+ sync-version.mjs 注入版本 + wails build（原生本平台）+ package-tool（正确 -os/-feBin/-beBin）。Go 环境显式注入 GOPROXY/GOTOOLCHAIN，不依赖 shell profile。
- 根 package.json 脚本改为：`build` = `npm run build:web && node scripts/build-desktop.mjs`；`build:go` = `node scripts/build-desktop.mjs --steps backend`；`build:desktop` = `node scripts/build-desktop.mjs`。
- 验证：macOS 上 `npm run build` 成功产出 `flore-portable-darwin-amd64-0.1.0-20260803.zip`，含 Flore.app + florebackend（权限 -rwxr-xr-x），无 .exe 残留；build/bin 自动清理上一平台二进制。同一条命令在 Windows/Linux 将自动产出对应平台包（原生构建，非交叉编译）。
- 注意：此改动（package.json + 新增 scripts/build-desktop.mjs）尚未提交。

## 「获取失败」根因定位与修复（2026-08-04 下午，关键）

- 用户反馈：窗口能显示，但首屏"获取失败"，且**等 15 秒以上、重开多次都无效**（证伪"轮询窗口太短"假设）。
- **根因**：`florebackend` 此前被 `package-tool` 放在 `.app` 包**外**（zip 顶层），且**完全未签名**（`codesign` 报 `code object is not signed at all`）。macOS 对从网上下载的包打 `com.apple.quarantine`，`Flore.app` 主程序被 Wails ad-hoc 自签名、用户点"仍要打开"能显示窗口；但它启动的子进程 `florebackend`（包外未签名独立二进制）被 **Gatekeeper 静默拦截** → 后端永远起不来 → `goStarted` 恒 false → 前端 `initApiBase` 轮询永远拿不到真实端口 → 回退默认 `localhost:3002` → 首屏请求失败弹"获取失败"。
- **为何本机验证"后端正常"是假象**：agent 沙箱/本机无 quarantine，包外未签名后端也能跑；真机下载包才触发拦截。
- **修复**（`apps/desktop/cmd/package-tool/main.go` 的 `buildPortable`，darwin 分支）：
  1. 把 `florebackend` 拷贝进 `Flore.app/Contents/MacOS/florebackend`（包内，与 `Flore` 同级）；

  3. `findBackendByExecutable`（backend.go）本就从 `MacOS/` 同级 first-hit 命中，查找逻辑无需改。
- **附带的 UI 修复**：
