## 自动抓取失效 RCA + 修复（debug-rca）

**症状**：桌面程序后台挂机一晚无自动抓取，手动正常。日志 `florebackend.log` 显示 scheduler 每 5 分钟跑但 `getDueSources()` 常返回 0。退出为手动更新测试包导致，非 Bug。

**根因**：`adaptiveNextCheckAt`（source_service.go）在 `newCount==0` 时把 `NextCheckAtUnix` 设为 `now + fetchMaxInterval`（默认 4320 分钟=3 天），无新增源被推到 3 天后不再调度。前端"默认抓取间隔"(`defaultInterval`) 仅作用于新建源的 interval 字段，与后端调度 `fetchMaxInterval` 是两回事；UI 文案"订阅源将按此间隔自动抓取更新"误导。

**修复**（用户拍板：defaultInterval 改为全局调度间隔，硬刷新，修正文案）：
1. `source_service.go:adaptiveNextCheckAt` — 调度周期统一取全局 `defaultInterval`；`newCount>5` 缩短到 minInterval，否则按全局间隔轮询（不再推 3 天）。保留 interval 参数兼容调用链。
2. `scheduler.go` — 新增 `resetStaleNextCheckAt()`，启动时把被旧逻辑推到远未来的 `NextCheckAtUnix` 拉回 `now`（仅 `nextRetryAtUnix=0` 的源）；在 `Start()` 首轮前调用，自动校正存量数据。
3. `SettingsModal.tsx` — 文案改"全局抓取间隔"+准确描述。

**验证**：`go build ./...` 通过；前端改动仅 JSX 字符串，tsc 无错。
**部署**：后端需重新 `wails build` 打包；存量校正随 scheduler 启动自动执行，无需手动迁移。

## 文章列表排序异常 RCA + 修复（debug-rca，@user 报障）

**症状**：全部文章/文件夹视图看不到最新文章，仅单源视图正常。DB `C:\opt\tools\Flore\data\reader.db`。

**根因**：`Item.pubDate` 列类型混用——2691 条 text（ISO 空格格式 `2026-08-04 12:36:44+08:00`）+ 256 条 integer（毫秒）+ 67 条 null。SQLite `ORDER BY pubDate DESC` 按**类型分组**排序而非按时间值，text 组（即使更旧）恒排于 integer 组（即使更新）之前 → 新文章沉底。

**为什么产生混用**：
- 新建走 `Create(&Item{PubDate: NullableMilliTime})` → `Value()` → integer（正确）
- 更新走 `Updates(map)` 且 `updates["pubDate"] = it.PubDate`（原始 `time.Time`）→ 绕过 `Value()` → GORM 默认序列化写 text（BUG，fetcher.go:574）
- 旧 v2 迁移用 `time.Parse(RFC3339Nano)` 无法解析空格格式 → 2691 条 text 从未被转换（迁移本身已失效）

**修复**（3 处，已 `go build`+`go vet` 通过；DB 副本实测 2691/2691 转 integer 成功、TOP 10 变真实最新）：
1. `fetcher.go:574` — `updates["pubDate"] = models.NullableMilliTime{T: &it.PubDate}`（写入端堵漏，GORM Updates(map) 对实现 driver.Valuer 的类型会调用 Value() 写 integer，已实测）
2. 新增 `migrate_v5_pubdate_strftime.go` + `migrations.go` 注册 + `CurrentSchemaVersion=5` — `UPDATE Item SET pubDate = CAST(strftime('%s', REPLACE(pubDate,' ','T')) AS INTEGER)*1000 WHERE typeof(pubDate)='text'` 幂等转换存量。DB 当前 schema_version=4，下次启动自动触发 v5
3. `time.go` `parseMilliTime` 增 `strings.Replace(v," ","T",1)` — 读取端兼容空格格式（双保险，实测空格/T/整数三格式均可 Scan）

**关键验证**：text 空格格式用 RFC3339Nano 必失败（空格非 T）；GORM `Updates(map)` 对自定义 Valuer **会**调用 `Value()`。

### 9. RSS 重复 link 导致 chinawriter 源抓取失败（同日追加，8月5日）

**用户报障**：`https://rsshub.icecome.com/chinawriter/404057` 无法读取内容。DB 中源 34（文史-中国作家网）0 篇文章，`SourceHealth.fetchFailCount=834`，`lastError="UNIQUE constraint failed: Item.sourceId, Item.link"`。

**根因**：RSSHub 为该源生成 RSS 包含 40 条 `<item>`，但其中 18 条为重复 link（同一文章出现 2-3 次）。`filterValidItems` 仅过滤 `link==""` 不过滤重复 link，导致 `upsertSingleItem` 对同一 link 在事务内尝试两次 `tx.Create()` → 违反 `uniqueIndex:idx_items_link_source` → 事务回滚 → 整批 22 篇文章全部写入失败 → 每次抓取累计 834 次失败。

**修复**：`fetcher.go:filterValidItems` 增加 link 去重（保留首次出现）：
```go
seen := make(map[string]bool, len(items))
validItems := make([]FeedItem, 0, len(items))
for _, it := range items {
    if it.Link == "" || seen[it.Link] {
        continue
    }
    seen[it.Link] = true
    validItems = append(validItems, it)
}
```

**DB 修复**：重置源 34 的 `SourceHealth`（fetchFailCount→0, lastError→NULL, nextCheckAtUnix→0），下次自动调度即可正常抓取。

**验证**：`go test ./internal/services/ -run TestFilterValidItems -v` PASS；`go test ./...` 全通过；`go build ./...` 通过。
