## Bug 排查：搜索能命中但文章列表滚动找不到

- 现象：RSS 阅读器抓取文章后，搜索能找到，但在「全部文章」列表里滚动找不到；且问题源**未**配置时间线隐藏，该源文章「有的可见有的不可见」。
- **首轮假设（已推翻）**：源级 `hideInTimeline` 过滤导致列表/搜索不一致。**被数据库实跑数据推翻**——全库仅 1 个源 hideInTimeline=1（且 0 篇文章），且该字段是源级 all-or-nothing，无法解释「同源部分可见」。
- **真实根因（已用 DB 数据坐实）**：文章列表存在 **`limit=100` 硬上限 + 无分页/无限滚动** 的截断。
  - 前端 `useItemsData.ts:77` 恒发 `limit=100` 且从不发 `offset`；后端 `handlers/reader.go:677-685` `offset` 默认 0、上限 200；`ArticleList.tsx:139` 的 IntersectionObserver 仅用于滚动可见性，**无任何 load-more/分页**。
  - 列表查询 `GetItems`(`reader.go:325`) 按 `pubDate desc` 取全局 top-100；搜索 `SearchItems`(`reader.go:976`) 走 FTS5+LIKE，按关键词命中、不受该 100 上限约束（自身 limit 50 也不同）。
  - DB 实测：Item 总数 1470，列表仅返回 100（1370 条默认不可见）；无过滤规则（排除 markRead 自动已读假说）；问题源「部分可见」= 仅该源最新冠军少数几条挤进全局 top-100，其余被截断。
- 结论：根因是「列表 UI 只消费单页有界结果，缺少加载后续页的机制（分页/无限滚动契约缺失）」，与源级 hideInTimeline 无关。
- 修复方向待用户拍板：A) 列表加无限滚动/cursor 分页（推荐，治本）；B) 仅调大 limit（临时缓解，超量仍会截断）；C) 虚拟列表 + 分页结合（大库性能最优但改动大）。

## 二次修正：用户补充「源内第2篇不显示」特征后的再排查

- 用户补充：找不到的文章，按时间最新排序是**源的第二篇**（第1篇在列表能看到）。此特征先推翻了"全局 limit 截断"初判（用户认为第2篇不像截断），也排除了 hideInTimeline 源级（用户确认未开）。
- 进一步读代码：后端 `buildItemQuery`/`GetItems` 无 GROUP BY / row_number / 去重 / 按源分组逻辑；排序仅 `pubDate desc, createdAt desc`。前端 `useItemsData` / `ArticleList` 也无去重、`IntersectionObserver` 仅做 scroll/hover 自动标已读。默认 `filter = unreadOnStart ? 'unread' : 'all'`。
- **DB 实测（diagnose_rank.py）彻底坐实根因**：
  - 全库 1470 篇，**`isRead=1` 仅 3 篇** → 「未读过滤」假说被直接否决（几乎不可能隐藏任何文章）。
  - 扫描「源内第1篇可见、第2篇不可见」实例 8 个：第1篇全局排名 **42~67**（进 top-100），第2篇全局排名 **240~367**（被 `limit=100` 截断）。
  - 结论：「源内第2篇看不到」正是**全局「全部文章」视图 `limit=100` 截断的典型表现**——高频源只有最新 1 篇挤进全局前100，第2篇落到 240~367 名被截断。初判的 limit 截断才是真因，只是当时未把"源内第2篇 ⇄ 全局200+名"对应起来。
- 边界待确认：若用户是在「点进具体源」的源视图下仍看不到第2篇，则 src_rank=2 ≤100 不该被截断，本结论需推翻（可能 listSortOrder='oldest' 反向截断或其它），需用户确认当前所在视图。
- 诊断脚本：`diagnose_visibility.py`（总量/top100 计数）、`diagnose_rank.py`（源内排名 vs 全局排名对照）均可复跑。

## 续：抓取性能与列表更新时机对比（用户新提两问）

### 问题一：Flore 每次刷新遍历所有源慢，fluent-reader/Folo 快

- **Flore 现状（已确认）**：
  - 手动"刷新全部"：`POST /sources/fetch-all` → `FetchAll`(`handlers/reader.go:517`) → `Coordinator().SubmitAllSources()`(`services/coordinator.go:130`) 查询**所有 active 源**无差别提交，worker 池并发 10（上限 30）。
  - `FetchSourceFeed`(`fetcher.go:94`) 对每源**全量重拉整份 feed** 再 upsert，**无 If-Modified-Since/ETag/游标**等增量手段。
  - 节流**只用于后台调度** `runOnce`（`filterSourcesToFetch` 按 `interval`+`LastSuccessAt` 筛选，scheduler.go:201-217），**手动刷新不走节流**。
  - 日志 `flore-backend.log` 大量 `context deadline exceeded`(20s)/`HTTP 503` 僵尸源每次全量刷新都被重抓，严重拖慢。
- **fluent-reader 为何快**：`fetchItems`(`item.ts:223-235`) 用 `last + (s.fetchFrequency||0)*60000 <= now` **每源独立节流**，只抓到时间的源；大量低频源平时根本不抓。
- **Folo 为何快**：抓取/调度在**后端**；客户端同步用 `api().entries.list({publishedAfter,...})` **增量游标**只拉新文章（`entry/store.ts:525`），不主动全量重抓。
- **借鉴可行性**：
  1. 最小改动：手动"刷新全部"也复用 `filterSourcesToFetch`（只抓到期源），或新增"仅刷新到期源"模式；保留"强制全量"选项给确需时。
  2. 增量优化（治本）：`FetchSourceFeed` 加 `If-Modified-Since`/`ETag`（源上存 Last-Modified/ETag，304 时跳过解析+upsert），减少慢源/无新源开销。
  3. 僵尸源治理：失败源指数退避 / 临时禁用，避免每次全量刷新卡在这些源。

### 问题二：Flore 抓取期间频繁刷新列表，另两项目最终才更新

- **Flore 现状（已确认根因）**：`App.tsx:493-531` `useEffect`——`refreshing=true` 时 `setInterval(3000)` 每 3 秒轮询 `/sources/fetch-status`；在 `fetching=true` 期间每 3 秒全量调用 `fetchItems()`+`fetchSources()`+`fetchFolders()`+各 count（518-523）。注释明写"抓取期间渐进刷新，让用户实时看到新文章"（`App.tsx:517-518`）。**这正是"频繁更新列表"的来源。**
- **fluent-reader 为何最终才更新**：`Promise.allSettled(promises)` 等所有源抓完，一次性 `insertItems`+`fetchItemsSuccess`(`item.ts:250-281`)；期间每源完成仅 `dispatch(fetchItemsIntermediate())`(246) 更新进度/计数，**不刷文章列表**。
- **Folo 为何最终才更新**：后端游标分页 + 客户端 `useInfiniteQuery` 按需拉；未读计数事件驱动 + 远程同步；**不轮询列表**。
- **借鉴可行性（低成本、高价值）**：删除轮询体 518-523 行的渐进 `fetchItems/fetchSources/...`，仅保留 `fetching=false` 时调用一次性 `refreshAllData()`(`App.tsx:480-491`，已存在)。代价：抓取期间列表不实时更新——正好对应"另两项目最终才更新"的预期。可选增强：保留轻量进度提示（已完成 X/N）但不重拉列表数据。

## 自动加载 bug 审查：滚动到底不自动加载（P1-1 回归缺陷）

- 现象：整改后列表有「加载更多」按钮可点（能加载），但**滚动到底部不自动加载**后续页。

- 排除层：`App.tsx:1009-1011` 已正确传入 `hasMore/loadingMore/onLoadMore={loadMore}`；`useItemsData.ts:168-171` 的 `loadMore` 内部守卫 `if (loadingMore||loadingItems||!hasMore) return` 逻辑正确，非根因。按钮可用是因为其 `onClick` 是内联箭头函数，能拿到最新 `onLoadMore`。
- 产出文档：`docs/planning/auto-load-bug-analysis.md`（含 SPEAR 评分、M-R1 详情、5-Why、方案 A ref 同步 / 方案 B 依赖数组）。

## 网页模式回归第三轮：修复 style 标签剥离 bug + 懒加载图代理（2026-07-31，用户反馈仍有部分样式/CSS 代码外露）

- **现象**：部分网页样式能渲染一部分，部分完全无样式；页面底部/中部把 CSS 代码以文本形式显示出来（如 `.network-status { ... }`、`.backToTopBtn { ... }`）。
- **参考项目深探结论**：
  - Folo 桌面端：`IN_ELECTRON ? "webview" : "iframe"`，webview 直接加载原文 URL；无 HTML 代理、无 CSP 剥离、无 CSS 内联；通过 `onBeforeSendHeaders` 伪造 Referer/Origin；图片代理条件触发。
  - Fluent Reader：纯 Electron `<webview>` 直接加载 `item.link`；`partition="sandbox"`；无代理、无重写；链接/弹窗被 `will-navigate`/`setWindowOpenHandler` 拦截并外跳。
  - 共同点：**webview 是顶层浏览上下文，`X-Frame-Options`/`frame-ancestors` 对其不生效**，所以无需代理 HTML。Flore 用 Wails/WebView2 没有 `<webview>` 标签，只能继续 iframe + 代理 HTML，但应让浏览器尽量直连原站资源。
- **真正根因（ Flore 代理 bug）**：`server/go/internal/handlers/reader.go` `rewriteImageURLs` 第三步重写 `<style>` 内 `url()` 时，使用 `strings.Replace(match, content[0], rewritten, 1)`——`content[0]` 是完整 `<style>...</style>`，`rewritten` 只是内部 CSS，结果**把样式标签外壳整个剥掉**，CSS 文本直接暴露为页面内容。与截图症状完全吻合。
- **修复**：
  1. `rewriteImageURLs` style 重写：改为 `strings.Replace(match, content[1], rewritten, 1)`，保留 `<style>`/`</style>` 外壳。
  2. `<img>` 重写扩展：除 `src`/`srcset` 外，增加 `data-src`、`data-original`、`data-srcset` 的代理重写，覆盖常见懒加载实现。
- **校验**：`go build ./...` 0 错；`go vet ./internal/handlers/...` 0 错。
- **取舍**：Wails 无原生 webview 容器， iframe + 代理 HTML 是现有架构下的折中；直连原站 CSS/JS + 仅代理图片（修复 style bug 后）已最大限度接近参考项目行为。少数强防盗链/需 Cookie 的 CSS 仍可能缺失，但可通过后续引入原生 webview 窗口彻底根治。

## 修复网页模式无样式（2026-07-31，用户反馈显示不同文章但完全无样式）

- **现象**：上一版 src 方式修复后，网页模式能切换不同文章，但完全无样式（CSS 不生效）。
- **根因**：改为 `src` 方式时误删了 iframe 的 `csp` 属性。该属性为 iframe 内部文档设置独立 CSP（`style-src * 'unsafe-inline'` 等），否则 iframe 继承 Flore 父页面严格 CSP，代理内联/回退的 CSS 被 `style-src` 规则拦截，导致「无样式」。此属性并非 srcdoc 专用——对 `src` 加载的文档同样有效。
- **修复**：`apps/web/src/components/Reader.tsx` iframe 加回 `{...{ csp: "default-src *; script-src *; style-src * 'unsafe-inline'; img-src * data: blob:; font-src *; connect-src *; media-src *; frame-src *;" }}`。sandbox 仍不含 `allow-same-origin`，代理页 JS 运行在 opaque origin，安全。
- **校验**：前端 `tsc -b` 0 错。需重新构建桌面应用生效。

## 修复网页模式"已阻止此内容"（2026-07-31，csp 属性触发 WebView2 拦截）

- **现象**：加回 iframe `csp` 属性后，所有文章网页模式提示"已阻止此内容。请与网站所有者联系以解决此问题。"（WebView2 拦截整篇代理文档）。Folo / Fluent Reader 无此问题——它们用 webview 直连原站，不受父页 CSP 继承影响。
- **根因**：`iframe` 的 `csp` 属性在 **WebView2（Chromium 封装）中处理异常**，设置后整篇文档被拦截。该属性并非 srcdoc 专用，但对 WebView2 的代理文档会导致"内容被阻止"页面。
- **修复（CSP 改由响应头下发，WebView2 正确支持）**：
  - 前端 `Reader.tsx`：移除 iframe `csp` 属性（保留 sandbox 不含 allow-same-origin）。
  - 后端 `handlers/reader.go` `ProxyOriginal`：新增 `proxyCSP` 常量（`default-src *; script-src * 'unsafe-inline'; style-src * 'unsafe-inline'; img-src * data: blob:; font-src *; connect-src *; media-src *; frame-src *`），在**所有** text/html 返回路径（含 3 处错误页 + 正常 HTML）前 `c.Header("Content-Security-Policy", proxyCSP)`。iframe 内部文档用响应头 CSP，不受父页严格 CSP 继承影响，WebView2 正确渲染。
- **校验**：`go build ./internal/handlers/...` 0 错；前端 `tsc -b` 0 错。需重新构建桌面应用生效。

## 修复网页模式再次无样式（2026-07-31，移除服务端内联 CSS，根因闭环）

- **现象**：移除 csp 属性 + 响应头下发 CSP 后，网页模式**再次无样式**。至此桌面端网页模式经历「已阻止此内容 → 纯HTML文本 → 无样式」三轮回归。
- **真正根因（非 CSP）**：`ProxyOriginal` 默认路径调用 `inlineExternalCSS`——**服务端 `FetchCSS` 抓取原文 CSS** 内联成 `<style>`。原站对 CSS 做 Referer 防盗链 / 服务端抓取失败时降级 `/css-proxy`，一旦整条内联链路失败，整页 CSS 丢失 → 无样式。经验证据：`mode=minimal`（浏览器**直连**原站 CSS）样式正常，全量代理（内联 CSS）无样式 → 内联策略是元凶。
- **关键认知**：
  1. iframe `csp` 属性在 WebView2 会拦截整个文档（"已阻止此内容"），绝不能用。
  2. 仅靠响应头 CSP 救不了内联失败导致的无样式。
  3. 真实浏览器内核（WebView2/Electron）**直连原站**加载 CSS/JS 最可靠 = Folo / Fluent Reader 通用做法。
- **最终修复**（`server/go/internal/handlers/reader.go` `ProxyOriginal`）：
  1. 删除 `if mode != "minimal"` 分支，**不再调用 `inlineExternalCSS`**；
  2. HTML 处理改为**仅代理图片**（`rewriteImageURLs` → `/image-proxy`，设正确 Referer 绕过防盗链），**CSS/JS 保持原站直连**；
  3. 移除 4 处 `Content-Security-Policy` 响应头与 `proxyCSP` 常量，隔离完全交由 iframe `sandbox="allow-scripts allow-popups allow-forms"`（不含 `allow-same-origin`，脚本运行 opaque origin 无法访问父窗口，同时天然阻断站点 JS 的 `window.top` 反嵌入重定向）。
  - 前端 `Reader.tsx` **无需改动**：桌面端仍 `src` 加载 `/proxy/{id}`（无 mode → 默认直连 CSS + 代理图片），iframe 无 csp 属性。
- **校验**：`go build ./...` 0 错；`go vet ./internal/handlers/...` 0 错。行为对齐已验证可用的 minimal（样式可靠）+ 新增图片代理。
- **取舍**：保留 `inlineExternalCSS`/`/css-proxy` 等为死代码（重构范畴，按"修复 Bug 时不重构"暂缓）；少数强检测站点仍可能空白，但 sandbox 无 allow-same-origin 已阻断其对父窗口导航。

## 网页模式采用「预检分流 + 最小代理」方案（2026-07-31，用户确认落地优化版方案 A）

- **背景**：用户对比旧版 `rss_2`（2026-07-27）发现旧版网页模式"相对更好"——旧版直接 `src={item.link}` 直连原站、`sandbox` 含 `allow-same-origin`，后端 `/proxy/:id` 仅清 XFO/CSP + 注入 base，**不内联 CSS、不重写 URL**。当前版因过度代理叠加导致多轮回归。
- **方案**：参考 Folo/Fluent Reader（Electron webview 直连原站），采用预检分流：
  1. 后端新增 `GET /api/proxy/check/:id`（`CheckFrameable`）：轻量 GET 原文，检查响应头 `X-Frame-Options` / `Content-Security-Policy` 的 `frame-ancestors`，按原文 URL 缓存（`frameCheckCache sync.Map`）；不可嵌入→返回 frameable=false。
  2. 前端 `onToggleViewOriginal` 先调预检：frameable 且非混合内容 → `iframeSrc=data.url`（直连，sandbox 含 `allow-same-origin`）；否则 → `iframeSrc=/proxy/{id}`（最小代理，sandbox 去 `allow-same-origin`）。预检失败保守走代理。
  3. `ProxyOriginal` 退化为**最小代理**：保留 `stripCSPMetaTags` + 注入 `<base href>`/viewport/适配样式，**删除 `rewriteImageURLs` 调用**（不再碰 `<style>`/`<img>`），CSS/JS/图片全由原站直连。
  4. 混合内容处理（P1）：前端判断 `data.url` 为 http 且当前 https → 改走代理。
- **安全**：直连为跨 origin + `allow-same-origin`（安全，framed 站无法访问父窗口）；代理为同源，故去 `allow-same-origin`，脚本跑 opaque origin。
- **残留限制（iframe 架构固有）**：少数站点用 JS `window.top !== window` 客户端反嵌入检测，直连与代理都拦不住（需原生 webview 才无解），可加"在浏览器打开"作 escape。
- **校验**：`go build ./...` + `go vet ./internal/handlers/...` 0 错；前端 `tsc -b` 0 错。
- **待用户验证**：需重新构建桌面应用（`apps/desktop/build-desktop.ps1`）后重启 Flore 验证；若预检网络不可达会保守走代理。
