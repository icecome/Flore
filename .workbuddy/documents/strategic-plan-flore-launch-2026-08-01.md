## 1. 战略定位主张（来自路径）

### 1.1 核心判断

Flore 的问题**不是功能不够，而是功能已经跑到了交付能力的前面**。

| 维度 | 现状 | 评价 |
|------|------|------|
| 功能侧 | 58–65 个 API 端点，密度已达 Miniflux / Fluent Reader 量级 | ≈ 100 分 |
| 工程侧 | 测试覆盖 1.9%（38 个 Go 源文件仅 2 个测试文件）、无 CI、无 LICENSE、无自动更新、无崩溃上报 | 39.0 分 |

**倒挂比约 2.5:1。** 这决定了未来 3 个月的唯一正确动作是**停止加功能，把功能密度兑换成交付能力**。

### 1.2 一句话定位（分两版，随能力演进）

**版本 A —— 现在（Alpha 期）就能印在 README 首屏：**

> **Flore 是一个纯本地的 RSS 阅读器。**
> 你的订阅、全文正文和阅读记录只存在你自己的磁盘上——不上传、不注册、不联网也完整可用。
> 内置全文提取与 FTS5 全文搜索，让读过的东西真正沉淀成你自己的可检索资料库。

**版本 B —— 阶段 2 完成后（生态接入）替换为：**

> **Flore 是一个纯本地的 RSS 阅读器，也可以是你自己服务器的客户端。**
> 默认不联网、数据只在本地；需要多设备时，把它接到你自己的 Miniflux / FreshRSS 上，同步由你的服务器负责，Flore 永远不碰你的数据。

### 1.3 措辞纪律（采纳瑞思的判断）

- **全线禁用 "local-first"**，改用「纯本地 / local-only」。
- 理由：local-first 隐含"本地是主副本，但能同步"的承诺，Flore 没有后半句。用 local-first 描述一个 local-only 产品，收获的一定是差评。
- ⚠️ **需修改的确切位置**：`package.json:5` 的 description 当前写着 `"Local-first RSS reader with desktop support"`——这不是口径问题，是实体位置，已排入阶段 0。

### 1.4 明确放弃什么（写进 README）

| 放弃项 | 理由 | 何时重议 |
|--------|------|---------|
| **自建云同步服务** | RICE 仅 5.3，全表最低区。**成本构成经路径 v1.1 修正**：不是"重构全库 schema"（UUID 属 `ADD COLUMN` 增量迁移，Item 甚至不需 UUID 列），而是**软删除 + 操作日志 + LWW + 设备管理**四件长尾工程 | 12 个月内不重议 |
| **Fever 客户端的离线双主合并** | 取远端权威模式（D-A 选项 A）。双主合并等于把自建同步 80% 的难度搬进协议客户端，却只服务于该单一场景 | 阶段 3 退出标准全部达成后 |
| **移动端（iOS/Android）** | 单人产能下 ≈20 人周，RICE 3.3 全表垫底 | 有第二名贡献者后重议 |
| **全平台第一天对等支持** | Windows 优先；mac/Linux 阶段 1 只出「实验档」不承诺支持 | 阶段 3 转正式支持 |
| **与 Feedly/Inoreader 拼云端能力**（推荐流、AI 摘要、社交） | 与隐私定位直接冲突，且是云厂商主场 | 永不 |
| **成为"又一个自托管服务端"** | Miniflux / FreshRSS 已是王者，正面进攻无胜算 | 永不 |

> **一句话取舍逻辑：Flore 不做同步，Flore 接入同步。**

### 2.3 实跑门禁挖出的新风险（含数析独立复核修订）

| 风险 | 严重度 | 说明 |
|------|--------|------|
| **4 个陈旧 .exe 被 git 跟踪（含 SSRF 安全隐患）** | **高** | `apps/desktop/desktop.exe`(13MB) / `server/go/go-server.exe` / `main.exe` / `rss-server.exe`。`.gitignore` 有 `*.exe` 但已入库，规则不生效。**其中 3 个磁盘已不存在却仍被 git 跟踪，`git checkout` 会将其与未修复 SSRF 代码一并复活到磁盘**——这不是仓库臃肿，是可执行的安全隐患 |
| **HEAD 为带病旧版本，早于全部安全整改** | **高** | HEAD 是停留在 7-28 的拆分前大文件快照：`handlers/reader.go` 952→215 行、`App.tsx` 1125→502 行。它早于 P0/P1 安全整改、早于架构重构、早于 ArticleRow 构建阻塞修复。**磁盘一旦失效，能恢复的不是一个少点东西的 Flore，而是安全整改全部回退、且缺 2/3 源码的 7-28 快照** |

## 4. 用户视角与需求趋势（来自瑞思）

### 4.1 一个必须修正的定性

> **Flore 现在不是 local-first，是 local-only。** 二者在用户心智里是两回事。

### 4.2 最强反证：本地用户自己想要同步

**Fluent Reader 自己的用户呼声最高的两个 issue 恰恰是要接云服务：**

| Issue | 内容 | 热度 |
|-------|------|------|
| #4 | 接入 Feedly | **87 reactions** |
| #23 | 接入 RSS services | **39 reactions / 111 条评论** |

一群**已经主动选择了本地客户端**的人，最想要的功能是同步。"纯本地即卖点"被自己人证伪。

### 4.3 真正的分界线

> **不是"云 vs 本地"，是"单设备 vs 多设备"。**

单设备用户对无同步**完全无感**；一旦掏出手机，容忍度**瞬间归零——不是渐变，是断崖**。

这个判断直接决定：Flore 的可服务市场 = 纯单设备用户 + 愿意自托管后端的用户。前者盘子小，后者需要协议客户端能力才能触达。

### 4.4 目标用户分群

| 分群 | 核心诉求 | 与 Flore 匹配度 | 盘子 |
|------|---------|---------------|------|
| 隐私敏感的单机重度阅读者 | 数据不出本机 | ⭐⭐⭐⭐⭐ 最匹配 | 小 |
| 从 Feedly/Inoreader 逃离的迁移者 | OPML + 至少一种同步 | ⭐⭐⭐ 需协议客户端 | 中 |
| 自托管玩家 | 能当 Miniflux/FreshRSS 客户端 | ⭐⭐ 当前完全无法触达 | 中 |
| 中文内容重度消费者 | 非标准源 + 防盗链 | ⭐⭐⭐⭐ 已有弹药未宣传 | 中大 |

## 5. 需求池与发布准入定义（来自析客）

### 5.0　本轮新增关键风险：版本控制事实上未生效

本轮以只读方式复核 Git 状态时，发现一项此前三份分析均未捕捉、且**优先级高于已知全部阻断项**的风险。数析报告中的「Git 仅 1 commit」这一表述，严重低估了实际严重程度。

### 实测数据

| 核实项 | 实测结果 |
|---|---|
| HEAD 提交总文件数 | 226，其中 **88 个是 `.trae/` IDE 配置与技能包垃圾**，非源码 |
| 未跟踪的 Go/TS 源文件 | **136 个**（已排除 node_modules）｜路径 v1.1 独立复核口径：**150 个未跟踪文件，其中 93 个为 `.go`/`.ts`/`.tsx`**，另确认整个 `apps/desktop/` 桌面壳源码未入库。两组数字差异源于统计口径（是否含配置/资源文件），**结论一致，均按"全量纳入"处理** |
| 已跟踪但工作区已修改 | 62 个 |
| 已跟踪但工作区已删除 | **78 个** |
| Git 提交总数 | **1 个**（`git rev-list --count HEAD` = 1）——零历史，不可回滚、不可 bisect、不可溯源（路径 v1.1 追加，附录 A #18） |
| `docs/` 跟踪情况 | 磁盘 22 份 .md，**仅 1 份在版本控制内** |
| 被 git 跟踪的陈旧 .exe | 4 个，blob 合计 **80.4 MB**（desktop.exe 10.4 + go-server.exe 22.8 + main.exe 23.7 + rss-server.exe 23.6），其中后 3 个磁盘上已不存在，属幽灵条目 |

### 结论

Flore 约 18.6k 行代码的绝大部分**从未进入过 Git**，HEAD 与工作区已完全脱节。这不是「提交历史缺失」，而是**版本控制未生效**：代码仅存在于单台开发机的磁盘上，三份设计稿（cloud-sync-design / bookmark-collector-design / logging-skeleton-design）与 79 项整改记录同样不在版本控制内。

### 影响链

无可信源码基线 → CI 无从建立（CI 跑的不是将要发布的代码）→ 发布产物无法溯源 → 任何回滚不可能 → 开源、协作、LICENSE 叙事全部悬空。

竞析指出「无 LICENSE 是所有差异化叙事的前置阻断」，而**无可信 Git 基线是 LICENSE 的前置阻断**——在一个 HEAD 不含真实源码的仓库里放置 LICENSE，法律上覆盖的是一堆 IDE 配置文件。

### 对数析评分口径的影响

数析给出「发布工程 2/10」（经独立复核下调至 **1/10**），其评估依据是「无 CI、无自动更新、无签名、无发布流水线」。本项发现说明该维度被**系统性低估**：上述四项缺失均属"尚未建设"，而版本控制未生效属于"地基缺失"——它使发布工程维度的其余四项在技术上**无法被建设**，而非"暂未建设"。

建议对数析 8 维评分作如下解释性修订（总分已据此由 40.5 下调至 **39.0**；发布工程 **2/10 → 1/10**）：

> 发布工程 1/10 的构成中，扣分主因并非流水线缺位，而是**缺乏可信源码基线**这一前置条件。该项修复成本仅约 1 人日（因仓库仅 1 个 commit，重写基线几乎零代价），是全报告 **ROI 最高的单项**，其杠杆率超过原先被评为 ROI 最高的 B1（LICENSE，0.5 人日）——因为 B1 的价值本身依赖于本项先行完成。

对应需求编号：**REL-01，P0，约 1 人日**。

**数据分析师独立复核补充（2026-08-01）**：上述「地基缺失」进一步被证实为**带病旧版本**——HEAD 是停留在 7-28 的拆分前大文件快照（`handlers/reader.go` 952→215 行、`App.tsx` 1125→502 行），**早于全部 P0/P1 安全整改与架构重构**；`git checkout` 会把 4 个幽灵 .exe（含未修复 SSRF 代码）一并复活到磁盘。这把 REL-01 从「修复成本低」升级为「不修复即持续暴露已知漏洞」，对应第 2.3 节新增的两项高风险。数析据此将总分由 40.5 下调至 **39.0**、发布工程由 2/10 下调至 1/10，并新增零号阻断项 **B0**。

### 5.3　Non-goals（明确不做）

| # | 不做的事 | 理由 |
|---|---|---|
| 1 | 自建云同步服务 | 与数据主权叙事直接冲突，且引入永久运维成本与关停风险——这正是 Omnivore / Pocket 让用户逃离的东西；多端诉求改由 COMP-01 客户端路线解决 |

| 6 | Web 端 / 多用户服务端模式 | 会与 Miniflux / FreshRSS 正面撞车，而 Flore 的差异化恰恰建立在「单机零依赖」之上 |
| 7 | 插件系统 / 用户脚本引擎 | 直接击穿现有 DOMPurify + iframe sandbox + SSRF 逐 IP 校验体系，会使唯一的安全资产变为负债 |
| 8 | 自建 RSSHub 托管服务 | 运维与合规成本外溢，指引用户自建即可 |

#### 5.3.1　对「AI 能力」列入 Non-goals 的反驳

主理人倾向将「AI 摘要 / 翻译」列为 Non-goal，本章**不完全认同**，建议改写为：**「v1.x 不做；v2 仅以 BYO-Key（用户自带端点与密钥）形式评估」**。三点理由：

1. **BYO-Key 不违反数据主权**。用户自行配置端点与密钥，数据流向由用户完全掌控，这反而是「你决定数据去哪」的正面演示，与 GRW-02 叙事同向而非相悖。
2. **对中文用户是真实高频需求**。外语源翻译是中文 RSS 用户的普遍痛点，且 BYO-Key 模式下**零服务端成本**，是罕见的高价值低成本差异化。
3. **措辞留有余地更有利**。写死「永不做」会在开源社区造成不必要的对立与承诺负担，而「当前不做」保留了后续转身空间。

同理，对「AI 自动补全订阅列表 / 智能导出」一类设想的回应是：**这类能力的价值高度依赖已有的高质量本地数据，而 Flore 当前连跨源去重（CORE-01）都未实现**——在脏数据上叠加 AI 只会放大噪声。此类需求的正确排序是先补 CORE-01 与 QA-06，v2 再议。

**但需明确：本轮排期中不进入任何一条 AI 相关需求**，此点与主理人判断一致。

#### 5.5.3　该切片成立的三个硬前提

任一不满足则需重新排期：

1. **招募文案必须硬性筛除多设备用户**。瑞思指出的「单设备 vs 多设备」断崖是不可谈判的——**用招募门槛替代功能补齐**，是本切片能在 4 周内成立的唯一原因。
2. **README 首屏必须显式声明无自动更新、无同步、单设备定位**。否则用户预期落差将污染缺陷反馈质量，使 Alpha 的唯一目的（收集缺陷）打折。
3. **QA-01 降级版只保住「数据不可逆损坏」这一条底线**，功能性缺陷交由 50 名真实用户跑出来。这是拿人力换工时的自觉取舍，**Beta 前必须补齐全量 Tier1**（剩余 7–11 人日）。

#### 5.5.4　给路线图排期的两条拓扑提示

1. **REL-01 是全图的拓扑起点**。REL-02、REL-05 及一切 CI、发布产物溯源、回滚能力均依赖它先行完成，不可并行、不可后置。
2. **SEC-02（稳定 ID + 软删除，3–5 人日）已不再是 COMP-01 的硬前置**。协议客户端采远端权威语义（远端唯一事实源、本地只投影），不需要稳定 ID——该依赖经析客第 5 章 v1.1 合并勘误**撤回**。故 COMP-01 成本为 **11–16 人日**（非 8–12，亦非含 SEC-02 的 11–17）。**唯一例外**：若 D-A 选 B（双主合并），SEC-02 重新成为前置，COMP-01 涨至 14–21 人日。

## 7. 资源与风险登记册（来自路径）

### 7.1 单人产能下的三条取舍原则

1. **一次只开一条战线。** 单人开发没有并行能力，同时推两个方向的实际结果是两个都做不完。阶段之间**串行**，不重叠。
2. **零成本项无条件优先。** RICE 500–3000 的项目总成本不到 1 人周，却解除法律阻断和隐私矛盾。任何把它们排在功能后面的方案都是错的。
3. **能"接入"就不"自建"。** 协议客户端 34 分 vs 自建同步 5.3 分。单人团队的生存策略是复用生态，不是重建生态。

### 7.2 核心矛盾的排期化解：「功能已够但工程能力不足」

| 环节 | 内容 |
|------|------|
| **诊断** | 功能 ≈100 分 / 工程 39.0 分。在这个状态下**每加一个功能，都是在增加一份无法安全交付的资产**——没有测试保护、没有 CI 拦截、没有更新通道回收 |
| **化解手法** | **W4–W13 共 10 周功能冻结**，100% 产能投入交付能力（v1.1 因阶段 0 扩为 3 周而右移） |
| **可量化门禁** | 冻结期内 **API 端点数不得增加**（允许减少）。每周记录端点数，这比"我感觉没加功能"硬得多 |
| **为什么不伤用户** | 用户视角 6 项 MVP 底线中 4 项已满足，缺的 2 项恰好是冻结期交付物 |
| **心理账户** | 把覆盖率数字做成 **CI 徽章挂在 README**，让枯燥的测试工作产生可见的进度条 |

### 7.3 Top 6 风险登记册

| # | 风险 | 影响 | 缓解措施 | **触发预警信号** |
|---|------|------|---------|----------------|

## 8. 利益相关者沟通要点（三版本，来自路径）

### 8.1 高管 / 投资视角

- **市场判断**：RSS 阅读器市场没有空白，但有**错位**。服务端有王者（Miniflux/FreshRSS），Apple 生态有精品（NetNewsWire/Reeder），云端有商业化玩家（Feedly）。Windows 桌面端在位者 Fluent Reader 已于 2026-04 复活——我们面对的是**有活跃在位者的市场**，这已修正最初的乐观假设。
- **我们的位置**：唯一同时具备"纯本地隐私"+"中文内容生态适配"的桌面客户端。这两点云端竞品**结构上做不到**（隐私承诺与商业模式冲突），海外竞品**动机上不会做**（中文源规则维护成本对他们不划算）。
- **核心取舍**：**不自建同步，而是接入用户自己的服务器。** 量化依据：自建 RICE 5.3 / 约 12 人周；协议客户端 RICE 34 / 约 2–3 人周。**同样的用户价值，约六分之一的成本。**
- **诚实结论**：上线就绪度 39.0/100，**只具备限定范围 alpha 条件**。瓶颈不在产品力，在交付工程能力——极端到**连"把已有代码安全保存住"都尚未做到**（B0，见附录 A #18–21）。
- **资源现实**：单人业余开发（20–25h/周），净工作量约 100–135 人日、含缓冲后 **8.5–9 个月**至 1.0。**若引入第二名贡献者，移动端才具备可行性**——这是唯一值得考虑的资源追加点。
- **决策请求**：① 批准 **10 周功能冻结期**（W4–W13），这期间对外无新功能可宣传，但它是后续一切发布动作的前提；② 拍板**决策项 D-A**（Fever 客户端边界），建议取远端权威模式以锁死阶段 2 预算。

### 8.2 工程视角

**技术债偿还顺序（严格按此执行）：**

1. **W1–2 止血项** —— LICENSE / 日志追加 / 清理二进制（零成本项，总计 < 1 人周）；**日志脱敏（SEC-01）已非零成本项**，D8 升级后约 3–4 人日（覆盖 backend/desktop/frontend 三产出方 + ref/source/error 收敛，见 5.2.3）。`docs/planning/logging-skeleton-design.md` 已有成稿设计，评审通过即可动手。
2. **W3–12 交付基础设施** —— 测试 / CI / 自动更新 / 崩溃上报。靶子明确：`internal/services`(4440 行) + `internal/handlers`(2123 行) 占后端代码 **88%**，只投这两个包。
3. **W13–24 定向重构** —— 只拆**阻塞协议客户端接入**的 God 对象，不做全面重构。

**三个已定的架构决策：**

| 决策 | 结论 | 依据 |
|------|------|------|
| **同步架构** | ❌ 不自建 ✅ 做协议客户端（Fever API 优先） | 已核实 `models.go` 中 **5 处** `primaryKey;autoIncrement`，且全库**零 `DeletedAt`、零 `gorm.Model`**——无软删除意味着删除事件无法传播。**真正的成本不在 schema 迁移**（UUID 是 `ADD COLUMN` 增量操作），而在软删除 + 操作日志 + LWW + 设备管理；协议客户端消费对端 ID 空间并采**远端权威模式**（D-A 选项 A），**把这四件事整体绕开** |
| **跨平台** | ✅ 阶段 1 就做，成本被高估了 | Go 侧零阻断（纯 Go SQLite，无 CGO）。拦路虎仅 **5 处**硬编码：`wails.json:5/6/7` 三条 PowerShell 钩子 + `package.json:13` 的 cmd 语法（反斜杠路径 + `%npm_package_version%`）+ `package.json:14` 调 PowerShell 脚本。**1.5 人周量级** |
| **代码质量** | 维持"轻度屎山"现状，只做定向修复 | 八维评分中循环依赖 9 分说明主干架构干净，不值得大修。优先修**搜索竞态**和**备份恢复绕过 RWMutex**（曾致死锁）这类正确性问题 |

**测试策略**：不追求覆盖率数字本身。优先级 ① 抓取与去重逻辑（`fetcher.go`，用户数据正确性的命门）② 备份/恢复（数据安全）③ 过滤规则 ④ handlers 输入校验。

**被严重低估的加分项（应写进 README 而不是埋在代码里）**：`internal/services/urlpolicy.go` 有完整 SSRF 防护——DialContext 逐 IP 校验防 DNS-rebinding、云元数据域名黑名单（169.254.169.254 / metadata.tencentyun.com / metadata.google.internal / 100.100.100.200）、`isPrivateIP` 覆盖 RFC1918/loopback/link-local/ULA；`cmd/main.go` 仅绑 127.0.0.1、支持可选 `FLORE_API_TOKEN`（恒定时间比较）、CORS 白名单可配；前端 DOMPurify + iframe sandbox；IP 限流；备份名白名单正则。**这个安全水位高于多数同类开源项目。**

### 8.3 社区 / 用户视角

**Alpha 公告模板（限定范围，定向邀请）：**

> **Flore Alpha —— 一个纯本地的 RSS 阅读器**
>
> Flore 把你的订阅、全文和阅读记录**完整地留在你自己的磁盘上**。不注册、不上传、断网也完整可用。内置全文提取和 FTS5 全文搜索，读过的东西会沉淀成你自己的可检索资料库。
>
> **现在能做什么**
> OPML 双向导入导出 · 全文提取与阅读 · FTS5 全文搜索 · 文件夹与过滤规则 · 已读/星标/稍后读 · 代理与防盗链支持 · 本地备份与恢复
>
> **现在明确做不到（请在下载前确认你能接受）**
> - ❌ **没有多设备同步。** 这是当前版本的设计边界，不是待修的 bug。
> - ❌ **没有移动端**，12 个月内也不会有。
> - ❌ **目前仅 Windows。** macOS / Linux 构建正在打通中。
> - ❌ 不支持需要登录的私有源（Basic Auth 开发中）。
>
> **路上有什么**
> 下一个大版本的目标是让 Flore 能作为**你自己的 Miniflux / FreshRSS 的客户端**——同步由你的服务器负责，Flore 依然不碰你的数据。
>
> **这是 Alpha。** 我们会尽力，但请**先备份你的 OPML**。

**沟通三原则：**

1. **把"不做"写在"能做"旁边，字号一样大。** 隐私敏感用户是最挑剔的群体，厌恶被含糊措辞骗进来。前置声明"没有同步"会流失一批用户，但留下的是真正匹配的用户——这批人的留存和口碑价值远高于骗进来的量。
2. **只承诺方向，不承诺日期。** 单人开发的日期承诺兑现率极低，一次失信的代价远大于一次延期。用"下一个大版本的目标是……"，不用"预计 X 月上线"。
3. **把安全底子讲出来。** SSRF 防护、仅绑 127.0.0.1、可选 API Token——这些是隐私敏感群体真正在意的硬指标，目前完全没有对外表达，是被浪费的资产。

**必须避免的三种说法：**

| ❌ 不要说 | ✅ 改成 |
|----------|--------|
| "local-first" | "纯本地 / 数据只在你的磁盘上" |
| "同步功能即将推出" | "下一个大版本的目标是支持接入你自己的 Miniflux / FreshRSS" |
| "支持全平台" | "目前仅 Windows；macOS / Linux 构建正在打通" |
